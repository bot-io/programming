**a) Reseed — root cause unfixed, just guarded.** `packages/app/src/main.ts:763-767` (`onReseed`) → `rebuildSimulation()` (line 478) which commit `7e0f1e0` wrapped in `try/catch` (logs + `onError` overlay). The guard **swallows** the error instead of fixing it. The most likely real contributors are below (§2b grid, §2c unvalidated config). Note `onReseed` picks `Math.floor(Math.random()*2147483647)` — seed 0 is possible but harmless to mulberry32.

**b) SpatialHashGrid never resized — silent corruption (not a crash, but broken sim).** The grid is allocated **once** at startup (`main.ts:375-380`) sized to the *initial* `populationCap`. It is never recreated — every other site only calls `grid.rebuild()`. The Pop Cap slider (`controls.ts:486`) allows **50–2000**. Raising the cap above the original value makes `grid.next` (an `Int32Array`) too small; `insert()` writes for indices ≥ capacity are silently dropped (typed-array OOB), so those particles get corrupt/missing neighbor links → broken forces and (once eating uses the grid) broken eating. The grid must be recreated whenever cap or world size changes.

**c) Config deserialization has no range validation.** `config-schema.ts:394` `deserializeConfig` / `validateSpecies` (line 466) check only field *presence and types*, never numeric ranges. A hand-edited/imported/preset config with `maxSpeed: 0`, `radius: 0`, `populationCap: 0`, negative values, or `NaN`/`Infinity` passes validation and then causes runtime NaN/division-by-zero (e.g. `processLifecycle` `speed / species.maxSpeed` at `ecosystem-world.ts:199`). Range-clamp on load.

**d) `InteractionMatrix.set` has no bounds check.** `index.ts:537` writes `this.entries[typeA][typeB]` with no validation — contrast `InteractionRuleMatrix.idx` (`interaction-rules.ts:88`) which validates. An out-of-range species index (e.g. from a malformed matrix after add/delete) → `undefined` row → crash on next `get`.
