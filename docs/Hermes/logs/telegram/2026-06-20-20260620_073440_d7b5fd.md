## v1.0.53 — Timeout Root Cause Fixed

**What was actually killing it:** Three layers of "safety net" fallback code that turned 1 batch request into **up to 45 individual API calls**, each hitting the rate limiter, each retrying 3×. 

The chain:
1. Batch request → worker returns 429 (cooldown from a previous request)
2. `CloudTranslationServiceImpl` catches it → **falls back to 15 individual calls**
3. Each individual call → worker returns 429 again → `callProxy` **retries 3× with 1s delays**
4. `TranslatePageUseCase` catches THAT → **another 15 individual calls**

Result: 15 × 3 × 1s delays = 45s+ minimum, easily hitting the 120s timeout.

**Fixes applied:**

- **Ripped out all 3 fallback layers** — batch fails fast with a clear error instead of cascading into dozens of rate-limited calls
- **Exempted batch endpoint from IP cooldown** — batch is 1 API call regardless of page count, rate limiting it is counterproductive (verified: two back-to-back batch requests both return 200)
- **Removed Gemini thinking mode** — saves 3-5s per call
- **Batched state updates** — 15 translations applied in 1 list copy + 1 DB write instead of 30

APK at `C:\Users\Svetlin\dual-reader-1.0.53.apk`

I should have traced the full call chain end-to-end before shipping v1.0.51. The fallback cascade was an architectural time bomb — it "worked" in curl testing because curl doesn't trigger rate limits, but on a real device with the app making background requests, it was guaranteed to cascade. Won't happen again.
