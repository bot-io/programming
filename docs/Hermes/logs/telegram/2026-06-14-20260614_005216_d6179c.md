## 2. Current Force Architecture

**Force contract** (`core/src/index.ts:747`):
```ts
export interface Force<P> { readonly id: string; readonly params: P; apply(world, grid, dt): void; }
```

**Force classes — 8 total, all in `core/src/index.ts` except PointerForce:**

| Class | id | Location | Wired into app? |
|---|---|---|---|
| `PairwiseForce` | (no `id` — does *not* implement `Force`) | index.ts:650 | ✅ always on |
| `DragForce` | `drag` | index.ts:817 | ✅ toggle |
| `WanderForce` | `wander` | index.ts:933 | ✅ toggle |
| `PointerForce` | `pointer` | `pointer-force.ts` | ✅ toggle |
| `GravityForce` | `gravity` | index.ts:857 | ❌ **not wired** |
| `FlowFieldForce` | `flow-field` | index.ts:1040 | ❌ **not wired** |
| `VortexForce` | `vortex` | index.ts:1137 | ❌ **not wired** |
| `BoundaryForce` | `boundary` | index.ts:889 | ❌ (World.step handles boundaries directly) |

**Key architectural finding:** The core **already has a `ForcePipeline`** (index.ts:762) with `add()`, `remove(id)`, `get(id)`, `step()` — a fully dynamic force container. **But `main.ts` completely bypasses it.** Instead:

- Forces are instantiated as **hardcoded local variables** (main.ts:378–381): `pairwiseForce`, `dragForce`, `wanderForce`, `pointerForce`.
- Application is **hardcoded in `applyForces()`** (main.ts:587–596): explicit `if (dragEnabled) ...` calls for exactly 3 togglable forces + pairwise.
- Toggles are **boolean flags** (`dragEnabled`, `wanderEnabled`, `pointerEnabled`), not add/remove on a pipeline.
- Serialization (`config-schema.ts:303` `serializeForces`) is a **hardcoded `switch`** on force.id → `JsonForcesConfig` with fixed slots (drag, wander, gravity, flowField, vortex, pointer). Presets only populate `drag` + `wander`.

**Net:** The pluggable-force *foundation* exists in core but the app treats forces as a fixed set. Three force types (Gravity, FlowField, Vortex) are implemented, tested in `index.test.ts`, serializable — yet unreachable from the running app.
